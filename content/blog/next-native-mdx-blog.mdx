The goal for this blog is intentionally small: local files, static routes, and a rendering path that belongs to the framework already running the site.

## Why MDX

MDX keeps posts close to the code that renders them. It also means examples can live beside prose without introducing a CMS, separate metadata parser, or runtime renderer.

```mdx
import { defineBlogPost } from "@/lib/blog/metadata";

export const metadata = defineBlogPost({
  title: "Building a Next-Native MDX Blog",
  description: "A static MDX blog setup for Next.js.",
  publishedAt: "2026-06-13",
  tags: ["nextjs", "mdx", "systems"],
});
```

That shape keeps metadata in the post file while the slug remains filename-derived.

## Static by default

The public routes are generated from published posts only. Drafts stay importable for local work, but they do not appear in the index, RSS feed, sitemap, or generated post routes.

## Highlight once

Code highlighting happens during the MDX build. Shiki emits themed markup, and the app CSS maps that output to the current Catppuccin light or dark theme without client-side highlighting JavaScript.
